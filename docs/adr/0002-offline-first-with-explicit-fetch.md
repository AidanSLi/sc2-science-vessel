# ADR 0002 — Offline-first; network access is opt-in and cached to the local store

- Status: accepted
- Date: 2026-10-11
- Deciders: project founder

## Context

The founding requirement is "no account and no network required". One requested feature
conflicts with it: browsing SpawningTool's build-order library. Checked here:
`https://lotv.spawningtool.com/build/?matchup=PvZ` returns HTML (HTTP 200, 28,715 bytes,
`content-type: text/html`), and adding `?format=json` **still returns HTML**. No documented
JSON API could be found.

So "browse the SpawningTool library" cannot be both offline and live-scraped. Three
options were considered: (a) live scrape, (b) a build-time snapshot bundled with the app,
(c) a curated local corpus only (the user already maintains four matchup flowcharts in
`.mmd` form).

## Decision

The application is **offline-first and never requires a network at runtime**. The shipped
corpus is a **bundled snapshot** generated by a script in `tools/` from SpawningTool's
public build pages. Refreshing the snapshot is an explicit user action that requires a
network, and its output is written into the local store so the app works offline forever
after. A user can also paste a build string (SALT) directly, which needs no network.

## Consequences

- The core promise holds: no account, no network, no telemetry.
- The bundled corpus is frozen as of the last refresh; the UI must show its age and offer
  a refresh rather than silently presenting stale builds as current.
- We own a scraper. Its HTML dependency will break when SpawningTool changes markup, so it
  lives in `tools/` isolated from the app, and failure of the scraper must degrade to "the
  snapshot you already have", never to an error in the app.
- Auto-updating the snapshot in the background is explicitly rejected — it would make the
  app network-dependent again.
